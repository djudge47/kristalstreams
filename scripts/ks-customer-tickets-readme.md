# Customer Support ticket browsing and replies — October 24, 2026

The previous customer Support screen loaded all visible tickets once, did not filter the signed-in owner explicitly, retained the previous account's UI, and allowed delayed replies for an old ticket to populate the currently selected conversation. Its clickable div cards were not keyboard buttons. Ticket and conversation lists grew without paging, and reply insertion had no synchronous duplicate guard or returned-row confirmation.

## Resulting behavior

Only the current confirmed, non-anonymous verified account mounts the keyed workspace. Five compact ticket buttons are fetched per page with one look-ahead row, an explicit user_id filter and stable created_at/id descending order. Each ticket opens one keyed conversation with Back to tickets. The list's page survives that return and refreshes. Previous/Next and first-page recovery allow access beyond the API's default row ceiling without fetching all ticket descriptions into one long screen.

Each conversation read independently verifies Auth and rereads the exact ticket with id plus user_id before selecting replies. Replies use twenty-row pages with one look-ahead, latest page first and chronological order inside a page. Earlier/Newer controls replace the displayed page. Replies sit in a keyboard-focusable scrolling area capped at 320px so the page does not grow with the conversation. Request keys, aborts, generation guards, twenty-second deadlines and unmount cleanup prevent prior page/ticket/account responses from restoring old details. Missing tickets, failed reads and empty successful pages are distinct. Nothing treats a failed query as no tickets or no replies. The browser adds explicit filters/validation on top of existing RLS; it does not replace database authorization.

Reads use exact allowlists: support_tickets id,user_id,subject,description,status,priority,category,created_at; ticket_replies id,ticket_id,user_id,message,is_staff,delivery_status,created_at. Row identity, ownership, dates, bounded strings and duplicate IDs are checked. Reply author IDs are not rendered. Names and messages render as escaped text and wrap on phones. Navigation and save controls have 48px minimum height; ticket cards are full-width keyboard buttons.

Reply Save rechecks the current confirmed Auth owner and exact ticket before inserting only ticket_id,user_id,message,is_staff:false. Messages are trimmed and limited to 4,000 characters. A synchronous ref coalesces duplicate submissions, editing/navigation are disabled while pending, and success requires the exact returned ticket/author/message plus a valid server-created reply row. The message says saved in the ticket; it does not promise email delivery. Existing staff email acceptance/uncertainty labels are retained.

No automatic POST retry is allowed. Lost, malformed, empty or error results and a twenty-second write deadline are uncertain because the insert may have committed. The composer stays blocked. A fresh conversation read plus an explicit 'I checked the conversation — start a new reply' action clears the old draft before a new one can be written. Aborting transport does not guarantee reversal of a dispatched insert. This is a UI duplicate/uncertainty guard, not durable idempotency across reloads, tabs or remounts: existing grants do not permit browser-supplied reply IDs, and no grant/schema expansion was made to disguise that limit. Customers should inspect their conversation before manually resubmitting an uncertain reply.

Offset paging uses deterministic timestamp/UUID ordering but is not a transactional snapshot. Concurrent insertions/deletions can shift page boundaries; refresh/first-page recovery is provided. New-ticket creation, admin reply delivery, existing historical records and server email workflows are unchanged by this batch.
