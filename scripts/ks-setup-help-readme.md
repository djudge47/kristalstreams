# Customer setup-help handoff

The Preview dashboard's Get setup help link opens the existing client support form with only a `setupHelp: true` navigation flag. It puts no checkout ID, email, user ID, credentials or order claims in the URL or route state. The form independently calls the existing owner-scoped, read-only `ks-customer-setup` endpoint using the current sign-in token. Server-side getUser, purchaser filters, exact receipt/catalog checks and restricted database grants are unchanged.

The shared browser helper checks the response account ID, read-only/sandbox markers, bounded unique references, canonical tier/interval, valid timestamps, amounts, allowance and pending/unactivated state, then whitelists the returned fields. This is response validation, not a new source of payment authority. It is reused by the dashboard and support draft. A single order is selected automatically; several require an explicit choice. Arbitrary order objects in navigation state are ignored. Missing or unavailable saved details leave a general support form available; a changed/missing session clears order details and the typed draft, and requires sign-in again.

The setup form defaults to a Streaming category and a short editable setup-help subject/message. A read-only card shows the selected plan, test amount, allowance, receipt time and full support reference, and explains that the saved details, test/setup-pending labels and check timestamp will accompany the message. This snapshot is appended to the ticket description only inside the existing explicit Create Ticket handler. Opening the form, changing selection or checking order context sends no ticket, email, payment or provider action. The handler verifies the current user before inserting under that user's ID and rejects an account change against the loaded context. A synchronous local submission guard blocks parallel double-clicks; it is not a claim of durable exactly-once delivery after an ambiguous insert.

These ticket details remain customer-authored support text. They are not a trusted purchaser-to-line binding, a protected receipt attachment or authorization for billing/provisioning. No payment/CRM/provider status is changed by drafting or creating a support ticket. No new email trigger, database table, RLS policy, grant, API or production deployment is added.

On the setup-help entry path only, the phone view uses a Back to Dashboard link instead of showing the full client sidebar above the form. Desktop client navigation and ordinary support-form entry remain available. Form labels are associated with their controls, errors are announced, and Cancel/Create Ticket buttons stack at phone widths with usable tap heights. The previously reviewed dashboard layout and button placement are preserved.

Verification: five synthetic shared-helper checks cover owner/mode/whitelist, bounded distinct orders, malformed or forged status, invalid plan/amount/reference fields and the exact support snapshot. The seven existing customer API checks also pass. Full Vite build, scoped TypeScript and targeted React lint cover the changed TSX files; no real support ticket, email, purchase, provider call or database write is needed. Signed-in handoff/form review remains pending after Preview deployment. Do not submit a ticket merely to inspect the draft.
