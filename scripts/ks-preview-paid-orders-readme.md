# Preview paid orders awaiting activation

The private CRM has a manually refreshed **Paid orders awaiting activation** panel. Its GET-only API verifies the confirmed, nonanonymous administrator through Supabase `getUser` on every request, rejects Production and returns a bounded whitelist from at most fifty saved test orders. It is a saved payment view, not a current Stripe or provider status check. Account IDs bind payments to purchasers; editable profile labels are display text and never select or merge an existing streaming customer.

On Preview only, the existing shared `fulfill` flow verifies the Stripe Checkout Session, records it through `ks_apply_paid_checkout`, then queues the verified test receipt before requesting the existing deduplicated email alert. Both the signed webhook and authenticated owner confirmation already call this same flow. Unpaid/incomplete, other-account, currency, amount and environment mismatches fail before queuing. Queue failure returns a retry error with the receipt preserved rather than reporting successful activation. Email failures retain their existing retry behavior.

The new `ks_preview_paid_orders` table stores only a foreign key to the receipt, `awaiting_activation` and the first queue timestamp. A server-only SECURITY INVOKER transaction locks the immutable receipt, verifies its owner, test mode and exact catalog details, and inserts once. It rejects live or activated receipts. Repeats preserve one row and the original timestamp. No browser/public grants or policies expose this table; service_role has only SELECT/INSERT, and EXECUTE on the two invoker functions. The informational RLS-with-no-policy advisor entry is intentional for this server-only table. No SECURITY DEFINER or broad browser access is introduced.

Install `scripts/ks-preview-paid-orders-schema.sql` once. The migration does not replace the existing payment RPC, change customer profiles, modify live payment behavior or backfill records automatically. One previously verified successful sandbox receipt can be queued separately for review, without another Stripe checkout, email or provider request. Test orders remain separate from `iptv_customers` and `iptv_payments`, so they do not alter customer revenue statistics or fabricate provider line IDs, logins, passwords, expiry or renewal dates.

Verification includes six offline pending-order checks, the thirteen existing payment checks, a transactionally rolled-back database integration test for ownership/missing/live/underpaid receipts and replay, strict scoped TypeScript, targeted React lint, a full Vite build and API bundle validation. The database test verifies no customer, profile or payment history changes. Permission checks confirm no browser/public table/function access and no service-role DELETE. Signed-in review of the new panel remains pending until the deployed screen is checked.

This is intentionally limited to the existing Preview/test integration. The runtime adds no queue for live payments, the public site is not promoted, and no XUI activation/renewal or recurring card billing is enabled. Before production fulfillment, replace the legacy assumption that website-profile activation proves provider readiness, persist the approved package mapping, bind the customer/line, add durable per-order provider claims/reconciliation and verify provider results before marking streaming access active. Paid provider operations and reseller-credit spending require a separately approved concrete test.
