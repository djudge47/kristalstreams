# Pending setup support alert preparation

This staged handler and SQL prepare support alerts for **payment received, streaming setup pending**. The existing deployed Edge Function index, legacy handler, webhook, confirmation and receipt recorder are unchanged. Nothing in this update sends an email, applies a project migration, spends credit, creates service, or enables an automatic worker. This is a support notification; it is not a customer login/ready email.

After the complete receipt/queue rollout is ready, the same protected notification function can route explicitly to `pending-handler.js` with its existing backend authorization. The handler requires a current private receipt and canonical account identity, then a service-only SQL preparation checks the matching durable queue. Only `sessionId` is accepted from the backend request; sender and recipient cannot be supplied by the caller. The SQL freezes a plain-text message to support@kristalstream.com. Live messages say setup is pending; sandbox messages explicitly deny a real Stripe charge and credit authorization. Neither is a streaming-ready confirmation.

`ks_pending_order_alerts` retains one frozen payload and first-attempt time per queued checkout. Prior confirmed sends skip delivery. An existing legacy notification already delivered suppresses this new namespace; an ambiguous legacy attempt requires review rather than resending under a fresh key. Review-blocked, missing, mismatched and legacy-activated orders do not produce a new pending email.

For a prepared alert, the handler calls the fixed HTTPS Resend endpoint once with redirects blocked, an eight-second timeout, and stable key `ks-setup-pending/v1/<checkout>`. Concurrent/retried calls reuse the same frozen body and key. A database failure after provider acceptance can be retried within the safe window without inventing another delivery identity. After 23 hours, ambiguous sends stop for reconciliation before the provider's 24-hour deduplication window expires. A confirmed delivery is persisted with a locked, idempotent RPC; conflicting provider IDs require review. Guards reject changes to the payload, timestamp, or already-recorded delivery and prevent deleting history.

Provider contract checked against [Resend's idempotency documentation](https://resend.com/docs/dashboard/emails/idempotency-keys): keys are retained for 24 hours, with matching retries returning the earlier result. This preparation stops ambiguous retries sooner and preserves its payload beyond that window for manual reconciliation.

All proposed functions use SECURITY INVOKER and empty search paths with service-only EXECUTE. The proposed table has RLS and no browser grants/policies. Service UPDATE is restricted to delivery fields. No new Vercel function, client field, key, recipient or package dependency is introduced.

## Validation and rollout

Run `node scripts/test-ks-pending-order-email.mjs` for injected authorization, receipt/identity binding, fixed recipient/mode, send failure, acknowledgement loss, replay, concurrency key and expiry tests. Run `scripts/test-ks-pending-order-email-db.mjs` using the same temporary **@electric-sql/pglite@0.5.10** module as the receipt/queue tests (`KS_PGLITE_MODULE` points to its `dist/index.js` file URL). It loads the proposed schemas into isolated in-memory PostgreSQL with fictional identities and verifies freezing, permissions, legacy suppression and delivery replay. It has no project connection or live provider credentials. This does not prove actual provider delivery, deployed migrations or multi-session database concurrency.

Verified: 15 handler scenarios, 14 isolated PostgreSQL scenarios and the 12 existing order-email regression checks passed (41 total). One database scenario runs the actual handler against the proposed PostgreSQL functions and simulates provider acceptance followed by a lost database acknowledgement; retry keeps one provider delivery identity and records the result once. Targeted ESLint passed. A read-only project check confirmed that the new alert table/functions are absent and the existing completed paid test and unlocked reseller state remain intact.

Do not install the proposed SQL or route live notifications yet. Finish the worker/claim/recovery policy, new-customer-versus-renewal handling, live owner status/encryption/completion and UI states, then review one coordinated rollout. Notification failures must be recoverable independently from recording payment; they must not trigger a second line or another purchase. Existing frozen legacy messages stay untouched. General automatic spending and any additional real paid test need separate authorization.
