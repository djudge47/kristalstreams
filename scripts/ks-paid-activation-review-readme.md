# Read-only paid activation review

`Review paid activation` appears on each saved pending sandbox order in the protected CRM. It uses the existing paid-orders deployment function with the fixed `view=activation-review` selector. It is Preview-only, GET-only and independently verifies a confirmed administrator through server-side Supabase getUser. POST, forged enable flags, caller-selected owners/actions and unknown/multi-valued views cannot activate anything. There are still twelve API entrypoints.

The server selects the purchaser from the saved canonical payment queue. It retrieves that exact Stripe Checkout Session with its PaymentIntent/latest charge expanded, validates the owner/price/mode/paid state, and requires a succeeded intent with an exact captured, unrefunded, undisputed charge. The independently owner-filtered saved receipt must match the session and payment intent as well as its unactivated sandbox/catalog fields.

Auth admin getUserById and an owner-filtered profile read independently check the displayed customer identity/email. Prior trial operator activity, unconfirmed email, known active website/CRM access and an existing setup attempt are reported as blockers. Trial operator activity is a conservative stop, not a purchaser-to-line ownership assertion. Unknown eligibility/storage failures fail closed rather than implying eligibility. A matching known CRM email is never used to merge an account.

Fresh, read-only HTTPS/Fixie account/package reads bypass the warm admin cache. The standard twenty-package mapping supplies the selected package's exact credit cost, calendar duration, groups and allowance. The review shows cost, current balance and projected balance after a single creation in exact integer-millionth arithmetic. Insufficient credits, an unresolved reseller dispatch lock or missing encryption key remain blocked. Installed foundation/completion privilege status is checked; a provider snapshot older than thirty seconds cannot be displayed as current. The displayed balance is an estimate, not a reservation.

The shared provider read adapter contains only fixed GET user_info/packages/get_line operations and no form builder or write action. The real paid POST adapter reuses those reads internally. The deployed review imports neither the real write adapter, execution store nor SDK worker constructor. Bundle input checks verify that separation. The supplied API documentation and existing transport safeguards are unchanged.

No reservation, signing/issuance of approval tokens, spending approval, provider mutation, customer/profile change, email or other message occurs. Even a review with no blockers remains review_only, canActivate=false and creditApprovalRecorded=false. Real execution has not been released. The current administrator's existing test order may show prior-trial and website-access blockers; a separate confirmed prospective new customer and its own sandbox payment are prerequisites for a new-line test.

The browser whitelists the response and binds the administrator, saved customer, order, plan and amount before displaying it. It verifies credit arithmetic, snapshot age, blocker codes and all read-only flags. Auth/account changes clear the report, requests are aborted on unmount/timeouts and duplicate clicks are guarded. The panel stacks amounts for narrow screens and does not render an inoperative activation button. No credentials or raw provider/Stripe payload are displayed.

Warm-instance throttling prevents simultaneous/immediate repeat reviews after authentication; it is not a distributed lock or spending guarantee. Supabase reads have bounded fetch timeouts, Stripe retrieval uses a bounded timeout with no automatic retry, and provider reads retain fixed HTTPS/TLS proxy/no redirect/no direct fallback rules. Sanitized stage labels distinguish payment, customer and provider verification failures without returning raw errors or configuration values.

Run `node scripts/test-ks-paid-activation-review.mjs`: eleven checks use fictional Auth, Stripe, database and provider responses. They cover authorization/method/environment gates, exact saved payment/purchaser binding, visible estimates without capability, trial/access/lock/encryption blockers, independent result checks, failures/freshness, request throttling, fixed routing and browser whitelisting. The affected guarded worker/transport, foundation, queue, simulation and customer suites are rerun separately, with scoped strict TypeScript/React lint, full Vite build, shared API/internal worker bundles and function/import-graph checks. No schema or persistent data changes are needed by this update.

Before a real test, review/select an eligible new-customer account and its own sandbox payment, implement/review the single-purpose approval/reservation/execution entrypoint, and obtain separate explicit approval for its exact real credit impact before enabling/invoking it. Do not create a second line for the existing trial account, convert/renew that trial, change live entitlements or promote to production as part of review.
