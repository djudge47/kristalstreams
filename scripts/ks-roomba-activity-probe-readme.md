The diagnostic requires the owner's website admin session; Vercel authorization does not substitute for this application login.

## Follow-up: distinguish an unverified result

The owner's October 24 check returned `activity_unverified`; the original diagnostic collapsed every upstream failure into that result. It did not establish a permission failure, unsupported action, timeout, successful list or offline customer state. The route now classifies only locally selected diagnostic labels from the existing bounded transport: denied HTTP, rate limit, redirect, other HTTP error, timeout, unreadable body, unrecognized list, configuration or transport failure. It returns no provider message, body, field values, credentials, session identifiers or URLs. Authorization still precedes every cached outcome. Preflight throttling now supplies a fixed retry duration to the UI.

The UI maps these labels to fixed text and ignores raw response messages and unknown diagnostic text. Checking activity preserves a previously verified account result, and checking the account preserves the activity result. No cooldown completion dispatches a request. These categories narrow the next investigation; they do not establish why the provider denied a request or verify API version compatibility. The activity parser, single bounded request, endpoint, parameters, gates and Production configuration are unchanged.

The owner's next authenticated result specifically returned `response_unrecognized`: the JSON reader completed, but did not verify an activity list. It did not establish an HTTP or transport failure. The streaming reader now additionally reports only root/data container types, error-field presence and a closed allowlist of documented status codes (success, multi-success, failure, invalid input, no permissions; otherwise absent/unrecognized). No arbitrary status or customer value can reach the projection. The route distinguishes those three failure codes without claiming their underlying cause. It logs only the fixed category and validated shape, allowing remote investigation without needing repeated screenshots; authorization, request bounds and manual-only dispatch remain unchanged.

Reference rechecked October 24: the XUI Admin API response-shape section documents STATUS_FAILURE, STATUS_INVALID_INPUT and STATUS_NO_PERMISSIONS and says list results use data arrays. This is a diagnostic interpretation of a compatibility test, not proof that Roomba 1.5.5 implements that 1.7 action. The UI uses local text for every shape/status value, and rejects arbitrary format text. The account API entry is included in this change so the deployed diagnostic route is rebuilt with its reader.
