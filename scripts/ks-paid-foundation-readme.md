# Private Preview paid-setup foundation

This adds durable service-only attempt records and encrypted, owner-only streaming login handoff. It does **not** dispatch a provider request, spend credits, create a paid line, renew/convert a trial, activate a website profile or finish the live payment-to-CRM integration. There is no environment flag or browser action that enables a provider write. The existing in-memory simulator remains explicitly simulated.

## Durable records

`ks_preview_provisioning_attempts` binds one checkout session, payment intent and purchaser to one immutable package/reseller/allowance/bouquet/credit snapshot and encrypted pending login. Unique session, intent, owner and reseller/line keys prevent duplicate new-customer identities. A service-only reservation RPC locks and revalidates the existing pending sandbox receipt against canonical plan prices/durations and requires an explicit new-customer review assertion. Prior trial operator activity conservatively stops for separate review; that operator ID is not treated as a verified purchaser-to-line ownership binding. An existing trial must never be silently replaced by a new line.

The only allowed state transitions are reserved → dispatching → provider_verified → credentials_ready, with dispatching → reconciliation_required as a permanent stop. A one-time begin RPC locks the attempt and returns true only for the first dispatch claim. There is no retry TTL, reset or automatic second send. A lost claim reply also requires reconciliation rather than blindly issuing a request. Verified result recording rechecks the claim, reseller/package/username hash, allowance, exact groups and plausible provider-reported future expiry. It does not calculate a customer expiry from receipt fixed-day counts. An atomic completion RPC creates one owner/order/attempt login binding after verification; it does not claim that CRM/account activation or actual login delivery succeeded.

All new tables have RLS enabled and no browser grants/policies. Functions use SECURITY INVOKER, empty search paths, revoked PUBLIC/anon/authenticated execution and explicit service-role execution. The service role has no DELETE grant on attempts and no UPDATE/DELETE grant on login bindings. Triggers reject immutable binding changes, backwards transitions, plaintext-shaped envelopes and wrong-owner login bindings. Foreign keys retain audit records. These controls survive a process restart because they are database state, unlike simulator fixtures. They do not replace a future authenticated approval/transport/reconciliation worker.

`reserveDurablePaidSetup` is an internal adapter using verified paid-session validation, exact current mapped packages, account-scoped reads and the reservation RPC. Concurrent/lost reservation replies can recover by safely reading the same bound record; no provider send occurs. It returns no claim token, password or envelope to an API. It is not wired to checkout, the webhook or a paid execution route. Future execution must again verify Stripe/payment ownership, new-customer eligibility, package/account freshness, credit approval and the durable claim before issuing the single permitted request.

## Login encryption and handoff

`KS_LOGIN_ENCRYPTION_KEY` must be a separately generated, canonical base64-encoded 32-byte secret configured server-side for this Preview branch. It must not use a VITE_ prefix, be copied from Stripe/Roomba/Supabase secrets, be pasted into a ticket/chat, or be committed. `KS_LOGIN_KEY_ID` defaults to `v1` and may identify the key without exposing it. Do not overwrite/regenerate a configured key casually: pending and delivered encrypted logins depend on the original key. Key rotation requires a reviewed decrypt/re-encrypt migration or key-ring implementation; it is not implemented here. If the key is absent/invalid, reservation/decryption fails closed. The foundation review exposes only a configuration boolean, never a secret or envelope.

Credentials are generated using cryptographic random bytes and sealed with AES-256-GCM, a fresh 12-byte nonce, 16-byte authentication tag and authenticated context binding version/purpose/environment/key ID/account/order/attempt. Cross-account/order/attempt swaps, altered ciphertext or a wrong key cannot decrypt. Plaintext byte buffers are cleared after encryption/decryption, while returned login strings necessarily remain in the authorized server response/browser memory. This protects stored data; it does not protect a compromised authorized server/browser. No plaintext password is stored in the database, URL, local/session storage, logs, PR or email. No real credentials or production key have been used in tests.

The existing customer setup function now shares three fixed views: ordinary no-view GET retains pending setup status; GET `?view=login-availability` returns only the confirmed account's unexpired verified login references; explicit POST `?view=streaming-login` with a session reference reveals only that verified account's encrypted login. Each view independently validates getUser, confirmation/non-anonymous status, Preview environment, server-side owner-filtered inner joins and every returned owner/reference/state/expiry. The API never trusts a browser-supplied owner. Reveal does not accept GET/prefetch. Responses are private/no-store and reveal uses no-cache headers; raw database/crypto failures are sanitized. Production returns 404.

The dashboard component is hidden unless a verified available login exists. It reveals credentials only on a deliberate button click, validates the response identity/reference and clears secrets on logout/account change, hidden tab, unmount or a one-minute timer. It does not copy credentials automatically or send email. Actual paid streaming availability is not inferred from payment alone. The pending-order panel and profile are unchanged. No real ready login exists yet, so there is no real secret to show during the current review.

GET `/api/ks-preview-paid-orders?view=foundation` is a separate administrator-only status view showing installed database protections, a valid key-configuration boolean and continued disabled provider execution. This and login views reuse the existing two functions; deployment remains at twelve functions. Unknown/multi-valued views cannot choose arbitrary actions. No hosting upgrade or visibility change is included.

## Verification

```
node scripts/test-ks-durable-paid-setup.mjs
```

The SQL test `test-ks-paid-foundation.sql` inserts synthetic receipts/attempts against two existing eligible user IDs held privately in transaction variables, exercises the real functions as service_role, asserts state/replay/ownership/immutable/privilege checks and rolls back every test row. Existing receipt tables were verified to have no external-action triggers. No auth users, emails, live lines or customer/profile records are created or changed by the test. Post-test counts confirm zero new attempts/logins and the existing single trial guard remains intact. These serial transaction tests verify real persistence rules and unique constraints; they do not substitute for a live concurrent provider execution test.

The full Vite build, scoped TypeScript/React lint and both shared API bundles are checked separately. Legacy Dashboard dependency errors in src/lib/api.ts and its existing PWA any-type lint diagnostics remain outside this change; the Dashboard source edit only adds the handoff import/render. Security advisors are compared before/after. No new SECURITY DEFINER is added.
