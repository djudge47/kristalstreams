# Guarded new-customer paid setup: private Preview review

This implements an internal paid-creation worker, bounded signed spending approval, fresh Stripe/provider verification, a durable reseller-wide dispatch lock and atomic Preview CRM/order/encrypted-login completion. **No API route, checkout or webhook constructs or invokes the real worker. No environment flag enables it.** The foundation review runs nine cases with fictional adapters and reports zero real writes. A separately reviewed authenticated execution entrypoint, eligible new customer and explicit approval of the exact real credit cost are still required before any real paid test.

## Worker boundary

`createInternalPaidSetupWorker` accepts only a Preview Stripe test key, constructs the fixed provider/store adapters, and verifies the current administrator with server-side `getUser` before calling the internal core. It replaces any input approver ID with the verified administrator ID. It is not imported by the deployed routes. The pure core accepts injected adapters for tests; those are not a public authorization surface.

Before dispatch the worker rereads the bound Checkout Session with its PaymentIntent/latest charge expanded. Canonical owner, mode, status, currency, amount, metadata and intent must match. The intent must be succeeded with the exact received amount; the captured charge must be paid, undisputed and unrefunded. Invalid/unexpanded states fail closed. Local completion retries repeat this payment verification but never repeat provider creation.

The service adapter verifies the prospective customer's current Auth user through `admin.getUserById`, requires confirmed/non-anonymous status and the same profile identity/email, then runs the SQL eligibility check. Known active website access, prior operator-trial activity, a completed Preview setup or a matching known CRM email stop for review. Email matches are conservative stops, never ownership merges. An explicit new-customer assertion is required at reservation. The provider guide does not document a reliable global line listing, so this does not prove the absence of every manually created external account; operator review remains necessary.

Fresh account and full package reads bypass the admin warm cache. The twenty standard mappings are recomputed and exact package fingerprints, reseller, allowance, calendar months, groups and credits must equal the immutable attempt. A two-minute HMAC review token binds the verified administrator, purchaser, checkout/intent, price, package fingerprint, reseller, exact credit cost and observed balance. A changed balance also requires a new review. Credit arithmetic uses integer millionths; costs with more than six decimal places are rejected. The approval secret is separate from the login encryption key. No raw approval token is stored or logged.

The database validates the claim, cost/expiry and caller-supplied administrator audit identity, requires known new-customer eligibility, and acquires one unique reseller-wide lock before changing the attempt to dispatching. The server is responsible for administrator authorization; SQL functions remain service-only SECURITY INVOKER and do not read or gain grants on `auth.users`. The old unapproved begin RPC now rejects calls. If the dispatch claim loses its acknowledgement, the worker sends nothing and the persisted state remains stopped. No TTL releases an uncertain reseller lock. Manual activity outside this worker can still change credits; an unexpected post-request balance requires reconciliation.

## Provider transport and verification

Only the supplied fixed HTTPS reseller URL, strict TLS on both Fixie hops and documented `create_line` multipart fields are used. There is one POST, no transport retry, no redirect and no HTTP/direct fallback. The adapter does not accept a caller-selected URL/action. Group fields repeat individually, and no `member_id`, `package_cost` or invented expiry is sent.

Creation and fresh `get_line` results must agree on line ID, generated username, owning reseller, paid/enabled flags, package, allowance, exact groups and provider-reported future expiry. The bounded streaming reader transiently compares the returned password with the generated encrypted login using constant-time byte comparison; it clears its check and never returns the password in the parsed line. Ordinary diagnostic reads continue discarding credentials. A missing or different password stops completion. The account must then show exactly the approved credit deduction. Parser, network, line, balance or persistence uncertainty stays locked for reconciliation; the worker never automatically sends a second creation.

## Atomic local completion

`ks_commit_preview_paid_setup` locks the receipt/attempt in a consistent order, validates the saved result and username hash, checks new-customer eligibility/identity conflicts and creates one CRM customer, activity and immutable owner/order completion binding. It binds the encrypted login, marks the Preview queue setup_complete and releases the reseller lock in the same transaction. A foreign key prevents a login handoff without its completion binding. Unique identity keys, replay checks and immutable attempt/CRM fields prevent replacement of an existing customer. Failure rolls back local changes while preserving the provider_verified result for a local retry. Ambiguous provider outcomes remain stopped; a reconciliation resolver is not released here.

The retained completion record keeps the administrator audit identity, approval hash, approved cost, observed pre-send balance and claim time after the transient reseller lock is removed. These server-only records have RLS, no browser grants/policies and restricted mutation grants. No new SECURITY DEFINER or Auth-table grant is added.

CRM rows are visibly marked Preview paid setup, with zero monthly price, no live payment row, no due date and no plaintext password. They are excluded from unpaid/due/overdue/revenue calculations and manual billing/date/edit controls. Their expiry/allowance come from the verified provider result. Completed orders leave the pending queue, and repeated Stripe fulfillment preserves their completed state. Website profiles and live payment receipt entitlement remain unchanged because this is a test-only workflow. The existing owner-only login handoff remains authenticated and private/no-store.

## Verification and release limits

Apply `ks-paid-foundation-schema.sql` before `ks-guarded-paid-execution-schema.sql` on a new environment. The expanded `test-ks-paid-foundation.sql` now requires both schema stages. In this project the equivalent tracked migrations were applied through the management connector, including permission/audit follow-ups; the checked-in schema describes the final shape.

Run `node scripts/test-ks-guarded-paid-execution.mjs` for twenty-two checks, including the same nine worker cases shown in the foundation panel. Stripe/provider/storage calls use fictional or intercepted responses. Run the expanded SQL test as a rolled-back transaction: it verifies real service-role dispatch approval, global locking, permanent ambiguity, CRM conflict rollback, atomic completion/replay, queue replay, restricted privileges and absence of live billing. Existing user IDs stay inside private transaction variables; temporary eligibility/profile changes and every synthetic record are rolled back. No real provider operation, email, payment or persistent customer/profile mutation occurs.

Full Vite build, scoped TypeScript/React lint, worker/shared API bundles, import graph/function count, affected regressions and security advisors are checked separately. Tests do not prove a real paid activation or concurrent remote-provider behavior. A successful foundation check remains `providerExecutionEnabled: false` and `liveTestReady: false`.

Remaining release work: review and add an authenticated single-purpose approval/reservation/execution entrypoint under the existing function budget; select a confirmed customer with no known existing access and a matching sandbox payment; review the exact package/credit impact; obtain explicit approval before enabling/invoking a real test; verify real credentials in the app and resolve ambiguous results through a separately reviewed reconciliation path. Production requires revising the legacy payment-only entitlement RPC, live ownership/renewal rules and webhook-driven orchestration before promotion. Trial conversion/expired renewals remain separately unverified. No additional trial creation, paid provider operation or production release is authorized by this code review.
