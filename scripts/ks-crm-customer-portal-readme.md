# Verified customer portal connection (Preview only)

The customer's dashboard and Subscription page show saved CRM service details and received-payment history separately from website plan entitlements. The existing History page remains streaming history. Payment receipts never imply service activation or extension; old $0 rows and unpaid/refunded rows are not displayed as received money. There is no online/current-stream count.

Imported CRM accounts are not website Auth identities. No email/name/username match grants access. An administrator opens **Link website account** on a CRM card, enters an exact website email, reviews the confirmed Auth UUID and streaming account, verifies ownership with the customer, checks the explicit consent box and saves. Saving creates one private identity link; it does not update a customer/profile/payment or call the provider. Repeating the same save is idempotent. A conflicting owner cannot overwrite a saved link. Ownership corrections require a separately reviewed support action; there is no automatic reassignment. Installing the schema creates **zero links**.

Both handlers require Preview, the exact active Supabase project, and server-verified `auth.getUser` with a confirmed non-anonymous account. Linking additionally requires the fixed administrator identity, same HTTPS origin, exact JSON input and revalidation of the reviewed Auth UUID, confirmation timestamp and provider ID inside the transaction. No customer-selected identity is accepted by the customer read API.

The private RLS-enabled `ks_crm_portal_links` table has no browser access. The three SQL functions are SECURITY INVOKER with an empty search path, executable only by service_role. Its Auth lookup grants the server role SELECT on only `id,email,email_confirmed_at,is_anonymous`; password columns remain inaccessible to that role. The customer endpoint passes only the verified user's UUID/email. The snapshot joins the immutable link, current Auth identity/confirmation and current CRM provider ID. A changed email, confirmation timestamp, provider identity, deleted record or excluded Preview source removes visibility rather than guessing a replacement.

Only allowlisted package/status/connection-limit/expiry fields and positive paid receipt amounts, methods, dates and optional requested package selections are projected. No credentials, internal notes, external payment references, profile metadata, provider keys or IP/streaming activity are read. All responses are private/no-store and vary by Authorization. Auth changes abort requests and clear visible details; stale asynchronous responses are discarded. Payment history uses 200-row keyset pages plus one lookahead, with an explicit **Load older payments** control. A missing link is distinct from unpaid/inactive service; read failures never claim missing payment.

`node scripts/test-ks-customer-crm.mjs` (with `KS_PGLITE_MODULE` set to pinned PGlite) checks the real SQL and real SDK HTTP parameter serialization using fictional accounts only. `node scripts/test-ks-customer-crm-ui.mjs` exercises the actual customer/admin components, including account switches and explicit link consent. Existing setup-status and protected login routes retain their behavior; the new views share existing Vercel functions. No production release, charging, email, renewal execution, credits or execution controls are changed.

## Streaming expiration takes precedence

The Subscription page waits for its own account's service check before showing legacy website-plan panels. A verified linked streaming account shows its actual saved package, allowance and expiration only; the older website tier and access-period panels cannot contradict those details. Loading, failed checks and sign-out do not fall back to a possibly unrelated website expiration. An unlinked account (or a deployment where this view is not enabled) can still read its website record, explicitly labeled **Website Plan Access Period** and described as separate from streaming expiration. This is display logic only: no profile, billing, service, payment, expiration or provider change. Actual component scenarios cover a conflicting one-month website record versus six-month/three-connection streaming service, loading/error/account-switch handling and correctly scoped unlinked website access.
