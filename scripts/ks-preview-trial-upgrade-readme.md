# Existing-trial upgrade review

The selected customer policy is to retain an existing trial's streaming username and password when moving to paid service. This change adds a **review only** control to the administrator-owned test order in the private Preview CRM. It does not implement an upgrade or persist a purchaser-to-line binding.

`GET /api/ks-preview-trial-upgrade?sessionId=...` verifies the confirmed administrator through Supabase `getUser`, finds the saved pending sandbox order and requires its purchaser account ID to equal the signed-in administrator ID. This narrow workflow is for the administrator's controlled test only. It must not be generalized by matching emails, labels, usernames or the administrator who created a trial. Orders for other purchasers have no review control and are rejected server-side before trial or provider reads.

The endpoint then invokes the existing GET-only saved-trial checker, which verifies receipt ownership and the CRM identity. A linked saved trial is required. It reads the current normalized package catalog through the existing fixed HTTPS/Fixie `packages` reader, using its authentication, 60-second warm cache, failure cooldown, streaming limits and redirect/fallback restrictions. No caller can choose an action, target line, package, cost, credentials or upstream URL. The standard-family matcher checks all twenty plan/connection combinations and obtains the chosen paid package from actual returned fields. No real catalog values are committed in source.

The response whitelists the payment reference, existing saved trial identity/expiry, proposed paid package, duration, exact credits, connection allowance, channel-group count and package-check timestamp. Its immutable labels are `draftOnly`, `providerActionSent: false`, `credentialsPolicy: keep_existing` and `requiresCurrentLineCheck: true`. Passwords are neither loaded nor copied. No final expiry is invented. The current provider line and explicit customer-account binding must still be verified before an approved operation. A response is not a signed approval token and cannot authorize execution.

The review explains that a Stripe test payment does not make a paid provider upgrade free. No provider POST/edit/create request, reseller debit, email, database mutation or service activation is added. Trial creation remains disabled and its spent single-attempt guard remains intact. Six synthetic tests cover environment/method/auth, purchaser ownership, saved-trial conflicts, whitelist/override rejection, package failure and invalid receipt/identity fields. Signed-in review of this panel remains pending after deployment.
