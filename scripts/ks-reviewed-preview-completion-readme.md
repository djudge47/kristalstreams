# Reviewed Preview completion database bridge

This bridge connects a saved review reservation to the **existing guarded Preview completion transaction**. Unlike the preceding rehearsal, the SQL uses the application's payment receipt, queues, provisioning attempt, verified fulfillment, CRM and encrypted owner-login tables. All test users, payments, approvals and provider proofs are fictional. No provider operation is included.

## Required evidence

`ks_complete_reviewed_preview_setup` requires the exact claim, purchaser, provisioning attempt, private attempt token and verified username. The claim stays `reserved_for_review`; it never becomes dispatch authorization. A reserved, dispatching or uncertain attempt cannot complete. The attempt must already be `provider_verified` by the separately approved guarded worker.

The wrapper locks the profile, receipt, durable queue and claim in their established order, then the existing attempt. It calls `ks_commit_preview_paid_setup`, preserving that function's verified provider proof, explicit approval audit, CRM identity checks, encrypted owner handoff and old queue/dispatch release. The new completion audit independently matches purchaser/order/intent/reseller/package/connections/months, exact credit cost and balance-before, saved package fingerprint binding, prior reservation/approval timing, CRM identity/expiry, both verified owner bindings and pending review slot. Existing live or legacy-activated receipts are rejected. No profile entitlement or receipt expiry is changed.

The canonical attempt hash is reconstructed from the established ordered server JSON fields, including the reviewed package fingerprint. It must not be replaced with a hash of `jsonb::text`, whose object order/whitespace differ. Tests exercise a changed fingerprint and the existing byte-for-byte hash generated by the real helper.

Review policy revocation does not undo separately approved provider work that has already been verified. It can still be completed locally, without dispatching again. The original claim's UTC budget day is retained for settlement rather than charging the day of a retry. Unknown/expired provider proof, mismatched cost/balance/identity or a queue already marked for manual review stops the entire completion transaction.

## Atomic writes and restricted bookkeeping

The new `ks_setup_review_completions` table has one immutable audit per claim, attempt, purchaser and checkout. It records exact before/after spent and reserved units. Only the trusted backend can read/insert it; browser grants are revoked, RLS is enabled and all new functions use SECURITY INVOKER with an empty search path. No Auth-table SELECT grant or SECURITY DEFINER workaround is added.

The same transaction completes the actual Preview CRM/owner-login records, inserts the new audit, marks the durable queue complete, moves exactly the claim's cost from reserved to spent and releases its review slot. A failure at any later statement rolls back the earlier CRM/login writes and restores both slot/budget states. The original encrypted envelope remains unchanged. Lost function responses and exact repeats recover the same completed binding without another completion or settlement.

The staged review budget guard permits spent settlement only for the exact matching immutable audit and completed queue; it cannot reset spent credits, change the day/ceiling, or arbitrarily reduce a reservation. Slot deletion requires that same applied settlement. Completion/claim history cannot be deleted or rewritten. The claim's limited UPDATE privilege exists only for row locking; its guard rejects every actual UPDATE. A deferred constraint prevents a direct service INSERT from committing only an audit while omitting queue/budget/slot completion.

The server adapter first retrieves expanded settled sandbox payment evidence and independently checks the current confirmed Auth owner/profile email. It invokes only the one completion RPC and validates owner/order/attempt/claim/expiry/capability fields in the result. Unexpected fields and backend error details are not returned. No provider client or write adapter is imported, and no thirteenth API entrypoint is added.

## Remaining rollout work

It supplies no dispatch permission, policy seeding, scheduler, cancellation/reset/TTL, trial conversion, renewal or reconciliation resolver.
