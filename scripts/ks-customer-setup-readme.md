# Owner-scoped payment and setup status

`GET /api/ks-customer-setup` verifies the current bearer with Supabase getUser and requires a confirmed, non-anonymous owner. Caller-selected account IDs, emails and activation commands cannot choose another account. The endpoint writes nothing and makes no provider or email request. Responses use private/no-store caching and Vary: Authorization.

Preview reads up to five recent Sandbox queue/receipt rows, including pending and completed orders. Production reads the existing receipt-only queue for pending, review and completed entries; completed live entries remain review-only until a live completion contract exists. This read survives pausing new receipt-only orders. Development is unavailable. Query and independent row validation both enforce ownership, mode, matching references, catalog price/term/allowance and valid timestamps.

Completed Preview rows require a second, batched read of their fulfillment, credentials-ready attempt, receipt, CRM customer and encrypted owner-login binding. It selects no credentials or envelope. Missing or inconsistent proof fails closed. Verified current periods show saved setup confirmation and expiry; periods at or beyond expiry stay visible as ended, with no current provider-ready flag. Pending-only reads need no additional proof query. See `ks-completed-order-status-readme.md` for the full completion contract and evidence.

The dashboard clears details on account changes, aborts stale requests and supplies a manual refresh. Each card has its own pending, review, confirmed or expired state; a mixed list cannot give every order one progress label. Empty results do not claim no payment exists or service is ready. Errors distinguish unavailable status from payment failure and advise an already-paid customer not to pay again. Existing protected credential reveal remains separate.

Current validation includes real Supabase SDK query construction with intercepted responses, actual component initial rendering, and native PostgreSQL completion/expiry reads. It does not establish a deployed signed-in browser flow or current provider playback. No production promotion, live activation or new data access grant is part of this draft. Exact reports, counts and remaining work are in `ks-completed-order-status-readme.md`.
