# Customer payment received / setup pending preview

The customer dashboard now reads its own saved sandbox orders and separates payment confirmation from streaming readiness. This is a private Preview feature, not live fulfillment or a production rollout.

`GET /api/ks-customer-setup` verifies the bearer through Supabase `getUser`. A confirmed, non-anonymous account is required; administrator status is not required. The server uses only that verified user's UUID. Query/body user IDs, emails, checkout references, role flags and activation commands are ignored. There is no write method, checkout confirmation, provider call, email or automatic retry.

The server reads `ks_preview_paid_orders` with an inner join to `ks_payment_receipts`, filtering the joined receipt by the verified purchaser ID, sandbox mode, unactivated state and null expiry. The queue must still say awaiting_activation. Reads are ordered and limited to five rows. Every returned row is independently checked for the same owner, matching receipt/queue reference, fixed catalog price/duration/currency, pending state and bounded valid dates. An unexpected other-owner row fails the whole response without exposing it. No global admin-list RPC is used. Customer email, profile labels, payment intent, provider identity and passwords are not selected or returned.

Cache-Control is private/no-store and Vary is Authorization. Production/development return 404 before auth or storage access. Server-role credentials remain server-side and existing database RLS/grants are unchanged. The current foreign key supports the documented Supabase inner-join/filter query; no migration is needed.

The dashboard loads saved status once after its profile is available, with a manual Check setup status button and a 20-second abort. Duplicate clicks share no additional request. It validates the response account against the displayed profile, aborts on unmount/account changes, and clears old order details when the signed-in identity changes. Empty pending results do not claim that no payment exists or that service is ready. Unavailable status is reported separately from payment failure and directs an already-paid customer not to pay again. Production's 404 hides the panel.

The pending panel shows the purchased plan and allowance, original payment timestamp and support reference; it never substitutes the website plan's status for provider activation. Progress says Payment received / Streaming setup pending / Ready to watch not confirmed. All current sandbox entries carry a Preview/Test payment label and state that no real charge or service activation occurred. It supplies no streaming credentials, invented expiry, setup ETA or promise that a setup message has already been sent. Existing access, website-profile cards, support tickets and device-download guidance remain separate. Get setup help only opens the existing support-ticket form; it does not send a message.

Verification: `node scripts/test-ks-customer-setup.mjs` uses the real Supabase SDK against an intercepted synthetic fetch to inspect the exact joined query, ownership/filtering, auth/environment/method gates, no-write behavior, whitelist/bounds, catalog mismatch rejection and storage failure handling. It makes no network request, charge, provider call or database mutation. The new component passes strict TypeScript and targeted React lint, and the full Vite build and API bundle pass. Including the existing Dashboard dependency graph in strict TypeScript also reports eight pre-existing Promise/PostgrestBuilder mismatches in src/lib/api.ts; running the same check against the prior Dashboard reproduces those eight diagnostics. Dashboard lint reports its two unchanged PWA any types. These unrelated baseline issues were not changed. Signed-in customer dashboard review remains pending after Preview deployment. No new payment is needed: the existing confirmed sandbox receipt is sufficient.
