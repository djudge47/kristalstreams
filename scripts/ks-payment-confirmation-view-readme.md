# Payment confirmation and saved setup state

The shared fulfillment path records the canonical paid session separately from streaming completion. A completed Sandbox queue now triggers an independent read of its fulfillment, owner-login, receipt, credentials-ready attempt and CRM bindings. Confirmed or expired payment rechecks invoke no pending/setup email. Missing proof preserves the recorded payment and reports a verification problem with do-not-pay-again guidance. An unsupported live completed queue remains review-only.

`ks-payment-confirmation-view.js` validates payment mode, optional receipt reference and capability agreement. A Preview setup-confirmed result also requires saved expiry and check timestamps with an active period. At the expiry boundary the result becomes service-period-ended, preserving payment acknowledgement without claiming current readiness. A queue flag alone, website activation, malformed dates or live provider-ready data cannot produce the confirmed view. This presentation parser does not replace backend ownership/proof verification.

PaymentSuccess renders pending, confirmed, review and expired states. Expired and review views use an attention indicator and support action. Existing cancellation, retry, dashboard navigation and the legacy live website-plan redirect remain. Saved setup confirmation describes persisted verified service evidence, not current playback or fresh external provider health. The Sandbox payment did not charge a card; previous separately approved provider work may have used its authorized credit.

Dashboard and support views use the same completion/expiry contract per order. They no longer drop completed Preview queues or describe every support entry as a pending test with no streaming activation. Protected login reveal remains separate. No new checkout, provider write, email, API route or database change is introduced.

Current validation includes sixteen presentation/queue checks, nine actual-fulfillment/completion checks, twelve owner API checks, shared support validation and actual component renders. The native PostgreSQL suite feeds saved completion through the real status/support/payment parsers and verifies expiry without another setup. See `ks-completed-order-status-readme.md` for reports, exact totals and rollout limits. The live owner/completion/renewal/reconciliation lifecycle and connected release verification remain open.
