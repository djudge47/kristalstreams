# Receipt and durable setup queue preparation

This change prepares payment recording and an atomic durable setup queue without granting streaming or website entitlement. It is deliberately **not imported by any running route**. Its private SQL foundation was installed empty on October 18, 2026 as migration `20261018102053_add_private_receipt_setup_queue`, followed by the review-claim/completion support migrations documented in `ks-reviewed-preview-completion-readme.md`. The current checkout, webhook, confirmation, notification, existing trial and completed paid test retain their behavior. There is no new API entrypoint, package dependency, environment setting, provider request or credit authorization.

`_server/ks-receipt-only.js` validates the canonical paid Checkout Session, purchaser, mode, amount, currency, plan and duration before calling a separate service-only `ks_record_paid_checkout` function. It checks the returned owner/reference/plan/mode and whitelists response fields. It always reports `activated: false` and `provider_activated: false`; recording a payment cannot claim an XUI line exists.

The SQL inserts a canonical receipt and its matching queue entry in the same transaction, or reads an exact replay. It checks all immutable receipt fields, serializes on the profile before locking the receipt and queue, and preserves the original timestamps. If saving a new queue entry fails, its new receipt rolls back too. If a receipt was already saved before this path existed, a replay can recover the missing queue entry without rewriting the receipt. The independent `replayed` and `queue_replayed` fields distinguish those cases; the server rejects an unconfirmed queue.

It never updates a profile, expires or extends a plan, resets a device counter, changes an existing receipt, creates a CRM row, sends email or invokes a provider. An older activated receipt or one with an existing service expiry moves the queued order to `requires_review`; existing service remains intact. A repeated payment cannot reset that review decision. New receipts return `awaiting_activation` only after their queue obligation is durable. Neither state authorizes a worker to spend credit or proves that the purchaser is a new streaming customer.

`ks_setup_order_queue` stores one immutable receipt/intent/purchaser/environment/catalog binding and queue timestamp per checkout. A trigger verifies the binding against the canonical receipt and rejects deletion, identity/financial/timestamp changes, or reversal of a review decision. It has RLS and no browser policies/grants. The service role can select/insert and update only status; it cannot delete or rewrite bindings. The separately installed completion extension permits completed status only for its independently verified audit/owner binding, never an arbitrary status update. This recorder itself supplies no dispatch or completion API.

The recorder and queue guard use SECURITY INVOKER, an empty search path, and explicit service-role-only EXECUTE. Their private schema/grants are now installed, but no current route was changed. The original `ks_apply_paid_checkout` remains in use and still contains legacy live website activation behavior; this staged module does not fix that deployed behavior until a coordinated rollout replaces its callers. Do not rerun schema creation against installed objects; use new reviewed migrations for changes.

## Validation

`node scripts/test-ks-receipt-only.mjs` exercises the server boundary with injected RPC results; `node scripts/test-ks-payments.mjs` checks the existing recorder and catalog regression behavior.

`scripts/test-ks-receipt-only-db.mjs` uses **@electric-sql/pglite 0.5.10**, installed in a temporary directory outside this application, to run the proposed SQL in an isolated in-memory PostgreSQL instance. Set `KS_PGLITE_MODULE` to that package's `dist/index.js` file URL before running it. It boots fictional users and profile rows, uses the existing receipt-table DDL, exercises service/browser roles, both payment environments and all twenty plan/connection combinations, then destroys the instance. It has no connection string and does not contact Supabase. It does not prove real multi-session concurrency, deployed migration compatibility or end-to-end automatic activation.

Verified during preparation: 11 server-boundary checks, 19 isolated PostgreSQL scenarios, and 50 affected existing payment/queue/order-email/test-control checks passed (80 total). Targeted ESLint passed. The preceding receipt-only preparation also passed the full Vite build (10.30 seconds); this queue update changes no client or routed code. Subsequent migration and connected checks confirm an installed empty queue with browser access revoked. No payment receipt, customer entitlement, policy, reservation or provider balance was changed by installing the private foundation.

## Coordinated rollout still required

Before routing payments to this installed foundation, prepare the bounded worker/claim/recovery policy, distinguish authenticated new purchases from existing-service renewals, generalize encryption/owner status/completion for the live environment, and route notifications through a pending-compatible path. The staged handler/SQL in [ks-pending-order-email-readme.md](ks-pending-order-email-readme.md) prepares that alert separately; it is not deployed. The current email handler rejects unactivated live receipts, so changing only the recorder would cause avoidable notification failures. This receipt-only response validator also needs completion-aware handling before it can consume completed review queues. Completion must use provider-confirmed identity, allowance and calendar expiry, and must never resend an ambiguous creation. The queue is durable storage, not a scheduler; automatic claiming/execution is intentionally absent.

Update success/dashboard copy to distinguish recorded payment from completed XUI setup. Keep the automatic worker disabled until the whole path is verified with synthetic/failure/replay checks and a separately authorized deployment/credit policy. Do not silently reinterpret the earlier one-credit approval as authorization for general spending or another real paid test.
