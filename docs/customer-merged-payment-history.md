# Merged customer payment history

The customer's existing service panel shows one chronological history of recorded manual receipts and verified completed website renewals. A website row shows the full approved checkout amount, requested months/connections, **Payment recorded** timestamp, completion time and **Expiry recorded for this renewal**. The current saved service package/allowance/expiry remains above the history. A later service change does not rewrite the old receipt.

Website timestamps come from the durable receipt's `recorded_at`; they are not invented payment-received or settlement dates. A provider credit debit or an imported active service does not become a customer payment. Historical receipt amounts stay unchanged when future retail prices change; the reader does not reprice old orders against the current catalog. Pending/unbound website orders remain in their existing order-status panel. Refund/chargeback reconciliation, accounting balances and the administrator's payment/metric projections remain separate work.

The additive private `ks_client_crm_snapshot_v2(uuid,text,timestamptz,text)` function reads the current confirmed Auth/CRM link, legacy received receipts and immutable completed live renewal proof in one stable database snapshot. The website branch requires matching receipt/queue, review target, completed operation, provider proof/expectation and historical result, and exposes no provider identity, credentials or payment-intent ID. Exact same-customer/same-amount manual receipts referencing that checkout or Stripe intent take precedence over the website projection so the same payment is not displayed twice. No source record is rewritten or inserted.

The original UUID-cursor snapshot function and manual payment recorder remain unchanged. The v2 keyset cursor accepts a manual UUID or live checkout reference. Each source and the merged result has a 21-row bound for 20 displayed receipts plus lookahead. Stable time/ID ordering and exact timestamp precision preserve microsecond boundaries and mixed-ID ties. Browser validation checks source-specific identity, bounded historical receipt amount, months/allowance and completion timeline. Owner inputs come only from authenticated server verification.

Older and newer controls replace the displayed list rather than extending the page. Refresh returns to the latest page. An account change clears the payment/service records and navigation state. No new API function or provider request is added.

Disposable SQL tests cover actual completed renewal proof, unchanged financial rows, mixed manual/website keyset pages, microsecond ties, exact-reference deduplication, wrong owners, changed confirmation, fabricated DTOs and private roles. Actual mobile/desktop browser tests cover amount/date/expiry labels, bounded older/newer pages, refresh failure/retry and account switching.
