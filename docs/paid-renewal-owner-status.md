# Verified customer renewal history

A saved live paid renewal is displayed as **Renewal completed**, independently from Preview setup readiness or current streaming availability. Its completion date and **Expiry recorded for this renewal** are historical order facts. Current service allowance/package/expiry stay in the existing **Your streaming service** panel, which reads the currently linked CRM service. Later renewals, expired old terms and manual term edits do not rewrite old receipts.

The private invoker function `ks_owner_paid_renewal_completions(uuid,text[])` accepts one to five distinct live checkout references. It uses a single read snapshot of the immutable completion, saved provider proof/expectation, completed send operation/review identity, paid receipt, completed queue and currently confirmed Auth/CRM portal link. It reads no credentials or raw provider response and returns no customer/provider IDs. It has an empty search path and denies browser roles. Missing proof or changed ownership returns no verified completion, so the payment remains visible as requiring review. Storage errors remain unavailable and advise against paying again.

The existing owner endpoint verifies the signed-in confirmed account and independently validates the returned plan, amount, identity, mode and timeline. It whitelists the status, completion time and recorded expiry. The payment recorder performs the same proof read for a completed receipt replay; that return bypasses routing, new review preparation and pending email. It never calls XUI or grants website access. Both projections retain `providerActivated:false` / `provider_activated:false`; `renewalCompleted` reports historical local completion only.

The browser parser, dashboard order card, payment confirmation and generated support context distinguish this history from pending orders, review and Preview complete/expired setup. Existing controls are reused, including responsive layouts, touch-sized refresh/help controls, request aborts and clearing records on account change.

Verification uses fictional payments and actual disposable SQL. New database cases cover owner isolation, confirmation drift, bounded private permissions, later service changes and unknown/uncommitted completion. Actual browser journeys at 390px and 1280px cover historical expiry, mixed orders, unavailable/contradictory responses, retry and account switching. Existing checkout, receipt, Preview and manual renewal checks remain required.

This staged change does not add payment history, mark balances paid, update profile entitlements, retrieve credentials, enable execution, spend credits, send email or promote a deployment. The installed private completion backend still accepts only the separately reviewed six-month/four-to-three reset policy; additional provider policies and the executable transport bridge remain open.
