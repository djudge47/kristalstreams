# Administrator website receipt history

The command center's recent payments, customer cards and customer History now include verified completed live website renewals alongside existing manual payment records. Website rows show the original amount, **Recorded** date, completion time and expiry recorded for the renewal. They do not assert a current paid balance or current streaming access. Manual received dates and historical zero/pending/refunded rows retain their meaning; no customer payment or service record is inserted or changed.

An additive private stable invoker function, `ks_admin_website_payment_history(uuid,timestamptz,text)`, checks the current confirmed non-anonymous administrator from Auth, then joins the immutable receipt, completed queue/operation/review identity, expectation, provider proof and selected customer. It returns only payment display fields and the historical completion. It exposes no provider identity, credentials or payment-intent ID. A later customer confirmation, username or service edit does not erase the administrator's historical audit; customer-facing reads still require the current confirmed owner link.

The existing API function routes a GET-only `admin-website-payments` view with fixed-project/server-verified administrator authentication, strict cursor/query fields and private no-store responses. No actor/target override is accepted. The SQL returns at most 201 rows; the server displays 200 plus lookahead, and the client reads every keyset page. Every page and the final account identity are validated. A failed page, malformed response or account change discards the partial result. Website and manual reads run independently using the existing manual RLS access; a failure in either makes the combined payment read unavailable, without a manual-only fallback. This remains a recorded-payment view rather than an atomic accounting ledger.

The website projection suppresses a same-customer/same-amount received manual receipt carrying the exact checkout or Stripe intent reference. Existing manual IDs are also deduplicated when combining pages. Historical amounts are never repriced against today's catalog. Provider credit spending or imported activation is not converted into customer money.

**Payments This Month** includes eligible recorded receipts by New York calendar month, using manual received dates and website receipt-recorded dates. These totals are not net settlements or recurring revenue. MRR and customer billing fields are unchanged. Refund/chargeback reconciliation remains separate.

Customer History reuses the complete combined payment read, retaining older manual entries without the former 100-row query cutoff. Its payment list shows 20 entries per page with newer/older controls, and an unavailable read produces an error instead of an empty-history claim. The activity request has a generation guard so switching customers or closing History cannot apply a late response to a new selection.

Tests use fictional Auth, payments and intercepted HTTP/provider calls. Actual disposable SQL covers administrator-only access, historical audit after customer changes, pagination, revoked admin confirmation and unchanged financial rows. Handler/loader cases cover strict requests, whitelist validation, all 401 fixture receipts, failed later pages and changed accounts. Existing command-center/card tests cover source labels, preserved old amounts, recurring-revenue separation and New York month boundaries. Actual mobile/desktop History browser tests cover bounded pages, retained zero/refund/pending entries, unavailable/recovery states and changing customers.
